## はじめに

ZEN大学で知能情報を学んでいる2年生の松延です。AIエンジニアを目指して、AIエージェントの個人開発を続けています。

AIエージェントの話は、ここしばらくで重心が変わったと感じています。少し前までの中心は、「どう作るか」でした。いま日常の開発で起きているのは、「どう任せるか」です。エージェントを開発する時代から、エージェントに仕事を任せる（代行させる）時代に入った、というのが、いまの私の実感です。

これからのエンジニアに大事なのは、エージェントを作る力だけではありません。仕事をどう任せるかを設計する力です。この記事では、自分でエージェントを作った経験と、毎日 Claude Code と Codex に作業を任せている経験の両方から、任せるときに必要だと考えていることをまとめます。

## 作る話が中心だったころ

少し前まで、AIエージェントの話題といえば作り方が中心でした。どのモデルを使うか、ツールをどうつなぐか、RAGやメモリをどう設計するか。こうした話は、今でも大事です。

私も、自分用のAIエージェント「ヤタ（Yata）」を個人開発して、作る面白さと難しさを体験しました。ヤタは、自分のPCの中で動く個人用アシスタントです。チャットで日本語で話しかけると、調べものや、メール・予定の確認などを手伝います。作る過程では、モデルの選び方だけでなく、ツールのつなぎ方や、外に出る操作の前で人に確認する、といった設計も考えることになりました。

## 日常の開発で起きている変化

今は、ふだんの開発の進め方が変わってきています。私は毎日 Claude Code と Codex を使っていて、実装、テスト、調べもの、ドキュメント作成といった作業の多くをエージェントに任せています。

自分の役割は、「コードを書く人」から、「何をやってもらうかを決めて、結果を確かめる人」に近づいてきました。コードをまったく書かなくなった、という話ではありません。書くことと、任せて確かめることが、同じ仕事の中に並ぶようになった、という感じです。

## 「任せる」ときに必要になる4つのこと

任せる時代に必要だと感じていることは、次の4つです。どれも特別な手法ではなく、Claude Code や Codex に作業を渡すとき、先に決めておくと崩れにくい項目です。ここでは一般的な書き方と守り方を示します。特定の仕事がどれだけ速くなったか、といった数字は書きません。

### 1. タスクの切り出し：ゴールと完了条件を先に書く

エージェントに「うまくやって」とだけ渡すと、範囲が広がりすぎたり、途中で別の改善まで手を出したりしがちです。一回で終えられる大きさに分けて、ゴールと完了の条件を先に伝えます。

私が意識している書き方は、次のようなものです。

- **ゴールを一文で書く。** 例：「ログイン画面に、メールアドレスとパスワードのバリデーションを追加する」
- **完了条件を箇条書きにする。** 例：既存のテストが通る、新しいテストを足す、依頼した場所以外のファイルは変更しない、APIの形は変えない
- **やらないことも書く。** 例：デザインの刷新はしない、依存ライブラリの更新はしない
- **大きすぎる依頼は分割する。** 「この機能をよくする」ではなく、「まずテストを足す」「次に実装を直す」「最後にドキュメントを更新する」

完了条件があると、エージェントも自分も、「終わったかどうか」を同じ基準で見られます。終わったかどうかが曖昧なまま次の作業に進むと、あとから戻ることになります。

### 2. コンテキストの渡し方：前提・制約・触ってはいけない所

エージェントは、リポジトリの一部は読めても、頭の中にある前提までは知りません。先に伝えないと、使っていない書き方で直したり、触ってはいけないファイルを編集したりします。

先に渡すとよいのは、次のような情報です。

- **前提：** 何のプロジェクトか、どの言語やフレームワークか、いま困っていることは何か
- **制約：** 公開APIは変えない、コードの書き方はこのファイルに合わせる、新しい依存を足す前に確認する
- **触ってはいけない所：** `.env` や秘密情報、本番向けの設定、関係ないディレクトリ、自動生成ファイル。ロックファイルを勝手に書き換えない、など

Claude Code や Codex に渡すときは、「次のパスは変更しないでください」と明示するのが簡単です。秘密情報を含むファイル、デプロイ用の設定、自分以外が管理しているディレクトリ、などを具体的なパスで書きます。加えて、「変更してよいディレクトリ」を先に書いておくと、あとから差分の範囲を追いやすくなります。

全部を一度に渡す必要はありません。そのタスクに必要な前提と、外れてはいけない線だけでも十分です。

### 3. 検証：テスト・レビュー・評価で結果を確かめる

任せたあとに必要なのは、出てきた結果を確かめることです。テストが通った、と書いてあっても、テストの範囲が狭いことがあります。レビューをせずに取り込む前提には、していません。

確認の観点は、次です。

- **テスト：** 新しいテストがあるか、既存のテストを実行したか、失敗を隠す変更になっていないか
- **レビュー：** 依頼した範囲以外の差分がないか、意図しないリファクタや依存の追加がないか、秘密情報が混ざっていないか
- **評価：** 完了条件を満たしているか。満たしていなければ、どこが足りないかを次の依頼に書く

エージェントに「テストを実行して、結果を報告して」と頼むことはできます。ただ、報告をそのまま信じきるのではなく、自分でも差分を読み、必要なところは手元で動かします。検証は、任せることをやめる作業ではなく、任せる作業の一部です。

### 4. 権限と安全：自動でよい範囲と、人の確認が要る範囲

エージェントにリポジトリへのアクセスやコマンド実行を頼むほど、線引きが重要になります。全部を手動にすると任せにくく、全部を自動にすると、戻せない操作まで走りかねません。

線の引き方の例は、次です。

- **自動でやってよいことが多いもの：** コードを読む、テストを実行する、提案の差分を作る、作業用のブランチで編集する
- **人の確認が要るもの：** 強制的な git の上書き、ファイルやブランチの削除、秘密情報や本番設定の変更、本番へのデプロイ、公開（パッケージの publish や記事の投稿）、広い権限での新しい依存の追加

大事なのは、ツールが「できる」ことと、「やってよい」ことを混同しないことです。git で履歴が残る状態にしておけば、提案を試したあとでも戻せます。戻せない操作、外に出る操作、公開に関わる操作は、確認の側に置きます。

ヤタを作ったときも、メール送信や予定の作成のような、外に出る操作の前では人の確認を待つ、という方針にしました。任せる側でも、同じ考え方が使えます。エージェントに仕事を代行させるほど、止められる場所を先に決めておく必要があります。

## 作る経験と、任せる経験

4つの項目は、どれも進め方の話に見えます。ただ私は、エージェントの内側を作った経験があるからこそ、上手に任せやすい、と感じています。

モデルは、指示どおりに動くとは限りません。ツールは失敗します。コンテキストは足りなくなることがあります。権限が広いと、意図しない操作が走ります。作る側でそれを見ていると、「どこで止めるか」「何を先に伝えるか」「何をもって完了とするか」を、任せる側の言葉に翻訳しやすくなります。

作る経験と任せる経験の両方を持つことが、これからのAIエンジニアの強みになるはずです。どちらか一方だけ、ではありません。作れるからこそ、任せ方の設計ができる。任せてみるからこそ、次に何を作るべきかが見えてくる。いまの私は、その両方を行き来しています。

## おわりに

AIエージェントは、作るものから、仕事を任せるものへ、重心が移ってきていると感じています。作る話は終わったわけではありません。ただ、日常の開発では、Claude Code や Codex に実装やテスト、調べもの、ドキュメント作成を任せることが、すでに普通の選択肢になっています。

任せるときに私が大事にしているのは、タスクの切り出し、コンテキストの渡し方、検証、権限と安全の線引き、の4つです。特別なコツというより、先に決めて文章にする、という地味な作業です。

私はZEN大学で知能情報を学びながら、自分でAIを作り、AIに開発を任せる、の両方を続けています。同じように、エージェントとの働き方を試している人と、考えを交換できるとうれしいです。
