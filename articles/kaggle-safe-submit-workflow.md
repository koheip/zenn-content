## はじめに

Kaggleの作業を、LLMのエージェントやスクリプトに手伝ってもらいながら進めています。自動化すると楽になる反面、「確認しないまま提出まで進んでしまう」ような事故も起きかけました。

この記事では、Kaggle CLIでノートブックを扱う方法と、人の確認を必ず挟むためのラッパー、それから検証環境と本番環境の違いで学んだことをまとめます。

## 1. Kaggle CLIでノートブックの状態を確認する

### トークンの設定

新しめのトークン方式では、環境変数 `KAGGLE_API_TOKEN` にトークンを入れて使います。

```bash
export KAGGLE_API_TOKEN="（Kaggleで発行したトークン）"
```

### ノートブックの状態と出力を取る

Kaggle上で動かしているノートブックの状態確認と、出力の取得はCLIからできます。

```bash
# 実行中か、終わったか、失敗したかを確認
kaggle kernels status <ユーザー名>/<ノートブック名>

# 出力ファイルを手元にダウンロード
kaggle kernels output <ユーザー名>/<ノートブック名>
```

ブラウザを開かずに状態が分かるので、スクリプトやエージェントから扱いやすくなります。

## 2. 「うっかり提出」を防ぐ確認ラッパー

自動化したバッチが、確認なしで提出まで進んでしまったことがありました。提出は回数に制限があることも多く、取り消しもききません。

そこで、提出までの流れを次のステップに分けたラッパーを作りました。

1. **どのファイルを出すか表示する**
2. **y/Nで確認する**（Enterだけなら「No」）
3. **実行する**
4. **出力を検証する**（ファイルがあるか、形式が正しいかなど）
5. **提出コマンドは表示するだけで止める**

最後の提出は、表示されたコマンドを人が自分で実行します。こうすると、自動化の途中でどこかが壊れていても、提出の手前で必ず人の目が入ります。

確認部分は、たとえばPythonならこれくらいで書けます。

```python
def confirm(message: str) -> bool:
    answer = input(f"{message} [y/N]: ").strip().lower()
    return answer == "y"

if not confirm("このファイルで実行しますか？"):
    raise SystemExit("中止しました")
```

デフォルトを「No」にしておくのがポイントです。エージェントやスクリプトから呼ばれて入力がないときも、勝手に進みません。

## 3. 時間制限のある処理は、本番と同じハードで測る

手元の検証を速いGPUでしていたら、本番の遅いGPUとは結果の傾向が変わることがありました。

処理に時間制限があると、ハードが遅いだけで途中で打ち切られたり、時間内にできることが変わったりします。速い環境で「間に合う」と思っても、本番でも同じとは限りません。

時間制限がある処理は、**本番と同じハードで測る**のが大事だと学びました。

## まとめ

- Kaggle CLIは `KAGGLE_API_TOKEN` を設定すれば、`kernels status` と `kernels output` でノートブックの様子をブラウザなしで追える
- 自動化しても、提出の手前には必ず人の確認を挟む（デフォルトは「No」、提出コマンドは表示だけ）
- 時間制限がある処理は、本番と同じハードで測る

自動化を進めるほど、「どこで人が止めるか」を最初に決めておくのが大事だと感じています。
